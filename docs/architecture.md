# Устройство SofaStream

SofaStream координирует просмотр видео, которое каждый браузер получает от YouTube или RuTube самостоятельно. Сервер хранит состояние комнаты и передаёт события; видео фильма через него не проходит.

## Карта кода

| Каталог | Ответственность |
| --- | --- |
| `SofaStream.Domain` | Room, участники, ведущий, состояния Paused/Playing/Buffering, доменные события |
| `SofaStream.Application` | Команды и обработчики, интерфейсы репозитория и уведомлений, DTO состояния |
| `SofaStream.Infrastructure` | PostgreSQL, EF Core для записи, Dapper для чтения, миграции, доставка доменных событий обработчикам |
| `SofaStream.Api` | HTTP-контроллер, RoomHub, уведомления SignalR, ошибки, проверки готовности |
| `Frontend` | Обычные JS/CSS/HTML; адаптер плееров, SyncStateMachine, HTTP/SignalR, WebRTC, UI |
| `SofaStream.Tests` | Быстрые тесты домена и EF InMemory |
| `SofaStream.IntegrationTests` | Реальные миграции, EF/Dapper, HTTP и Hub на отдельном PostgreSQL |
| `tests/frontend`, `tests/harness`, `tests/e2e` | Клиентская логика, инструменты harness, браузерные сценарии |

Domain не зависит от веб-фреймворка или базы. Application зависит от Domain; Infrastructure реализует интерфейсы Application; API связывает сервисы.

## Изменение состояния

1. Браузер отправляет HTTP-команду.
2. Обработчик загружает Room и проверяет правила.
3. Room меняет состояние и создаёт доменные события.
4. EF Core сохраняет изменения.
5. Обработчики событий отправляют уведомления в группу SignalR.
6. SyncStateMachine применяет уведомление к адаптеру плеера.

Вход в существующую комнату дополнительно читает снимок состояния через Dapper. Клиент восстанавливает видео, позицию и состояние после готовности плеера; задержка получения снимка и загрузки видео учитывается при воспроизведении. Текущие ограничения перечислены в [backlog](backlog.json).

Сохранение в БД и доставка клиентам являются отдельными операциями. Восстановление по снимку важно при пропущенных уведомлениях.

## Контракты

| HTTP | Назначение |
| --- | --- |
| `POST /api/session`, `GET /api/session` | Выдать гостевую сессию или проверить текущую |
| `POST /api/room` | Создать комнату с именем, HostId и темой |
| `GET /api/room/{id}` | Снимок комнаты: видео, playbackState, currentPositionSeconds, snapshotAt, lastUpdatedAt, scheduledFor, участники, тема |
| `POST /api/room/{id}/join` | Добавить подтверждённого участника; лимит четыре включая ведущего |
| `POST /api/room/{id}/leave` | Немедленный явный выход |
| `POST /api/room/{id}/video/duration` | Сохранить известную плееру длительность для текущей версии видео; только ведущий |
| `POST /api/room/{id}/video` | Сменить видео; идентификатор пользователя, URL, заголовок и длительность |
| `POST /api/room/{id}/playback` | Состояние 0/1/2 и clientPosition в формате TimeSpan |
| `POST /api/room/{id}/playback/buffering-completed` | Сообщить о готовности участника |
| `GET /api/room/time` | Время сервера для оценки смещения часов |
| `GET /health/live` | Процесс принимает HTTP |
| `GET /health/ready` | База доступна, миграции применены |

RoomHub доступен по `/hubs/room`. Методы: `JoinRoom(roomId, userId)`, `LeaveRoom()`, `SendSignal(roomId, senderUserId, targetUserId, signal)`. Отправитель SendSignal определяется сервером; аргумент senderUserId оставлен для совместимости подписи.

События: `OnVideoChanged`, `OnPlaybackStateChanged`, `OnHostChanged`, `OnUserJoined`, `OnUserLeft`, `OnSignalReceived`.
Уведомление воспроизведения содержит `state`, `positionInSeconds`, `triggeredAt`, `scheduledFor`.
Начальный снимок использует другое DTO: `playbackState`, `currentPositionSeconds`, `snapshotAt`, `lastUpdatedAt`, `scheduledFor`; при изменении контрактов проверяйте обе ветки. Новые временные поля дополняют HTTP-контракт; формат уведомлений сохранён.

## Время воспроизведения и готовность плеера

Room хранит базовую `CurrentPosition` и `PlaybackStartedAt`. Обычный Play задаёт старт через секунду после команды; завершение буферизации возобновляет отсчёт сразу. Paused/Buffering и смена видео очищают отметку старта. Для Playing текущая позиция равна базовой плюс время после старта, не меньше нуля и не больше длительности видео. До будущего старта позиция не растёт.

Dapper рассчитывает позицию на `snapshotAt` через внедрённый `TimeProvider`. `lastUpdatedAt` обозначает время изменения воспроизведения, а `scheduledFor` присутствует только для ещё не наступившего старта. Клиент добавляет задержку от `snapshotAt` либо от будущего `scheduledFor`, поэтому уже учтённое сервером время не добавляется повторно. Позиции Paused/Buffering остаются фиксированными. Сравнение `lastUpdatedAt` с `triggeredAt` защищает более новое уведомление от устаревшего HTTP-ответа.

SyncStateMachine сохраняет последнее состояние до готовности API. UniversalPlayer отдельно сообщает о готовности выбранного видео: CUED у YouTube, `player:ready` у RuTube. Перед применением команд позиция пересчитывается ещё раз. Следующее состояние отменяет прежнее ожидание и запланированный Play; выход из комнаты также отменяет обработку незавершённого снимка. Эти фазы отражают [YouTube Iframe API](https://developers.google.com/youtube/iframe_api_reference) и [RuTube embed API](https://rutube.ru/info/embed/).

Браузерная часть разделена на файлы, но использует общие переменные и порядок загрузки. `runtime-config.js` позволяет локальному серверу передать адрес API; при обычном статическом размещении сохраняются стандартные адреса.

## Соединения и данные

HTTP-вход создаёт участника. Hub-вход связывает его с ConnectionId и группой. Отключение Hub удаляет участника, передаёт права ведущего и удаляет пустую комнату. Видеочат использует отдельные WebRTC-соединения и сигналы через Hub.

Идентификатор участника выдаётся сервером через `POST /api/session` вместе с защищённым Data Protection bearer-токеном на сутки. `GET /api/session` проверяет текущую сессию. Браузер хранит её в sessionStorage; HTTP использует Authorization, SignalR — accessTokenFactory. Query-токен принимается только на `/hubs/room`. Секрет не входит в снимки комнаты или уведомления.

Все операции комнаты, кроме времени сервера, требуют сессии. Переданный HostId/UserId должен совпадать с подтверждённым участником; снимок и команды требуют членства. Hub JoinRoom привязывает только уже добавленного HTTP-участника, не создаёт нового; SendSignal берёт отправителя из сессии и проверяет текущий ConnectionId, комнату и адресата. Замена соединения отзывает старую привязку. Тесты включают подмену идентификатора, анонимный вход, постороннего участника и параллельный приём.

Текущий запуск использует один процесс API. Изменения комнаты и обработчики подключения/отключения используют общий ограниченный semaphore, поэтому параллельный вход не превышает четыре участника и не пересекается с удалением. Для нескольких процессов этот механизм потребуется заменить блокировкой в БД. Ключи Data Protection должны сохраняться между пересозданиями production-контейнера; потеря ключей аннулирует выданные сессии. Сессия гостевая: учётных записей и восстановления личности после потери токена нет.

При обрыве Hub сохраняет участника и ведущего на 30 секунд (`Rooms:ReconnectGraceSeconds`, диапазон 1–300). Время отключения хранится в PostgreSQL. Периодическая очистка удаляет просроченных участников, передаёт роль и удаляет пустые комнаты. Новое соединение очищает отметку отключения; старое отключение проверяет только свой ConnectionId. После рестарта процесса прежние соединения помечаются отключёнными и получают то же окно восстановления.

Браузер при восстановлении повторяет HTTP join, подтверждает Hub-привязку и получает актуальный снимок, включая роль. Отложенные действия старого соединения отменяются; WebRTC-соединения создаются заново с сохранёнными локальными медиатреками. `POST /api/room/{id}/leave` или Hub `LeaveRoom` удаляет участника сразу. Выход во время восстановления отменяет применение запоздалых результатов. После исчерпания повторных попыток клиент возвращается к входу в комнату. Доставка WebRTC через NAT/TURN остаётся отдельной SS-007.

Любой подтверждённый участник сообщает Buffering и собственную готовность, а Play/Pause доступны только ведущему. Сервер вычисляет общую позицию остановки по временной шкале. Воспроизведение возобновляется после готовности или выхода последнего ожидающего. Ручная пауза и смена видео очищают ожидание. Буферизующийся плеер продолжает загружаться, затем останавливается до общего возобновления; готовность следует после подтверждения своего сообщения Buffering.

`Room.VideoRevision` увеличивается при смене видео. Снимок содержит `videoRevision`, OnVideoChanged — `revision`. Сообщения Buffering и buffering-completed содержат `videoRevision`; сервер отклоняет сообщения для старого ролика. Возвратившийся участник получает свою отметку IsBuffering из снимка и подтверждает готовность после подготовки видео.

## Решения первой версии harness

- Существующая архитектура приложения сохраняется.
- Быстрые и полные проверки доступны через один CLI и используются в CI.
- Интеграционные проверки используют PostgreSQL и реальный Hub; SignalR-клиенты в TestServer работают через LongPolling.
- Браузерные проверки используют настоящие HTTP и WebSocket-соединения, отдельные браузерные контексты и управляемый внешний плеер.
- Локальная база и временные тестовые базы изолированы от production-конфигурации.
- SDK и зависимости закреплены; будущие обновления меняют файлы блокировки явно.
- Версии EF Core согласованы на 10.0.6. Microsoft.OpenApi закреплён на 2.7.5, исправляющей обнаруженное NuGet предупреждение [GHSA-v5pm-xwqc-g5wc](https://github.com/advisories/GHSA-v5pm-xwqc-g5wc).

## Метаданные длительности и отклонённые команды

У нового видео Duration = 0 означает неизвестную длительность. Сервер не подменяет её одним часом. Ведущий получает положительную конечную длительность от внешнего плеера и сохраняет её через `POST /api/room/{id}/video/duration` с UserId и VideoRevision. Обновление метаданных не меняет позицию, состояние и версию видео; гость и запоздалый ответ для старого видео отклоняются. После получения метаданных сервер проверяет реальную верхнюю границу позиции. Начальное уведомление о видео дополнительно содержит `durationSeconds`.

Playback-команда содержит videoRevision. Клиент сохраняет миллисекунды, для позиций от суток использует формат TimeSpan с префиксом дней. Отказ HTTP и сетевая ошибка показывают причину и восстанавливают серверный снимок без повторного согласования WebRTC. Загрузка кадра во время Paused не создаёт флаг общей буферизации и не блокирует следующий Play.

## Размещение видеочата

Обычная комната использует сетку: плеер и управление находятся в основной области, видеочат — в `videoChatDock` сбоку. При ширине до 900 px чат располагается ниже плеера. Перенос в body больше не используется. В fullscreen чат и кнопка восстановления перемещаются в theaterContainer; перетаскивание ограничено с учётом панели управления снизу. При выходе из fullscreen чат возвращается в dock. Переносится существующий DOM с медиапотоками, без их повторного открытия.

## Задержанная готовность YouTube

UniversalPlayer существует независимо от загрузки YouTube API, поэтому вход в комнату и адаптер RuTube не требуют готового YouTube. Выбранное видео и состояние ожидают готовности управляемого плеера. Порог 4 секунды служит диагностикой задержки; поздний `onYouTubeIframeAPIReady` всё равно принимается, создаёт один YT.Player в существующем адаптере и восстанавливает актуальное состояние комнаты.

Независимый iframe с `autoplay=1` и фиктивный StubPlayer удалены: они показывали играющее видео при нулевых метаданных и не принимали команды комнаты. При ожидании показывается сообщение о загрузке, при ошибке API — предложение перезагрузить страницу. RuTube продолжает использовать свой iframe. Управление включается после готовности выбранного видео.

Первая загрузка не перематывает CUED-видео, если позиция уже совпадает с требуемой: [YouTube seekTo](https://developers.google.com/youtube/iframe_api_reference#seekTo) может запускать видео из CUED. Запоздалый нативный Playing при серверной паузе или до запланированного старта подавляется локальной паузой без новой команды серверу. Реализация и результаты проверок: [SS-010](tasks/SS-010.md).

## Громкость фильма

Громкость — локальное предпочтение браузера, доступное ведущему и гостю независимо. `audio-ducking.js` хранит выбранный уровень 0–100 в localStorage (`sofastream.volume`) и отдельно вычисляет фактический уровень фильма. При речи цель равна 30% выбранного уровня; при тишине и выходе возвращается выбранный уровень. UI сохраняет положение ползунка и показывает отдельный индикатор Speech, чтобы автоматическое приглушение отличалось от ручного изменения.

UniversalPlayer сохраняет последнюю заданную громкость даже до готовности iframe, затем применяет её после CUED/ready и при смене видео. Ползунок не отправляет команды серверу и не управляет громкостью голоса собеседника. Проверки: [SS-011](tasks/SS-011.md).
