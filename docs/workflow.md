# Рабочий цикл

Для каждой задачи определите пользовательский результат, затронутые части и критерии приёмки. Для небольшого исправления это может быть несколько строк в задаче или PR; большой задаче подходит [шаблон](tasks/TEMPLATE.md).

## До изменения

- Проверьте текущую ветку и пользовательские изменения.
- Выберите задачу из [backlog](backlog.json) или сформулируйте новую.
- Прочитайте соответствующую часть [архитектуры](architecture.md).
- Для исправления ошибки воспроизведите её и определите проверку, которая отличает исправленное поведение.

## Выбор проверок

| Изменение | Проверки |
| --- | --- |
| Только документация | Точность текста, существование ссылок и соответствие команд; тестовые наборы не нужны |
| Domain или Application | `npm run check`; интеграционные проверки, если затронуты сохранение, права или события |
| Контроллеры, Hub, EF/Dapper, миграции | `npm run check:full` |
| Синхронизация клиента или контракт API/SignalR | `npm run check:full`; оба пути: начальное состояние и уведомления |
| Только визуальные стили | Браузерная проверка затронутых экранов; скриншоты при полезности |
| YouTube/RuTube или WebRTC | Релевантные автоматические проверки плюс ручные сценарии из runbook |
| Harness, команды запуска, зависимости или CI | `npm run check:full`; запуск/остановка dev и воспроизводимость установки, если затронуты |

Используйте меньший релевантный набор при разработке, полный — при изменениях на границах компонентов. После успешной проверки повторяйте её при новых изменениях или конкретном сомнении.

## Готовность изменения

Результат включает:

- изменение, соответствующее критериям приёмки;
- осмысленную регрессионную проверку для исправленной ошибки;
- результаты выполненных проверок и пути к отчётам;
- обновлённую документацию, если изменились команды или контракт;
- перечисленные ограничения и незавершённые критерии.

Правило в AGENTS.md описывает процесс. Реальные ограничения доступа задаются средой агента; обязательные проверки перед merge следует настраивать в GitHub. Этот harness поставляет CI, но не изменяет настройки защиты ветки автоматически.

Агент может выполнять локальную реализацию и проверки в пределах принятой задачи. Авторизация на внешние действия учитывается отдельно. В этой первой версии агент приносит готовое изменение для ревью; постановка задач, merge и deployment остаются управляемыми пользователем.

## Следующий этап автономности

Текущие команды дают ненулевой код ошибки и машинную сводку с `schemaVersion`. Backlog хранит идентификаторы, статус, зависимости и критерии. Это точки подключения будущей очереди задач.

Переход к автономному режиму потребует изолированных рабочих копий, выделенных ресурсов/портов, лимита повторных попыток, независимого ревью и проверки результата перед подготовкой PR. В первой версии такого диспетчера и фоновых запусков нет.
