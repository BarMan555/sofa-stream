# Рабочий цикл

Для каждой задачи определите пользовательский результат, затронутые части и критерии приёмки. Для небольшого исправления это может быть несколько строк в задаче или PR; большой задаче подходит [шаблон](tasks/TEMPLATE.md).

## До изменения

- Проверьте текущую ветку и пользовательские изменения.
- Выберите задачу из [backlog](backlog.json) или сформулируйте новую.
- Прочитайте соответствующую часть [архитектуры](architecture.md).
- Для исправления ошибки воспроизведите её и определите проверку, которая отличает исправленное поведение.

## Выбор проверок

| Изменение | Проверки |
| --- | --- |
| Только документация | Точность текста, существование ссылок и соответствие команд; тестовые наборы не нужны |
| Domain или Application | `npm run check`; интеграционные проверки, если затронуты сохранение, права или события |
| Контроллеры, Hub, EF/Dapper, миграции | `npm run check:full` |
| Синхронизация клиента или контракт API/SignalR | `npm run check:full`; оба пути: начальное состояние и уведомления |
| Только визуальные стили | Браузерная проверка затронутых экранов; скриншоты при полезности |
| YouTube/RuTube или WebRTC | Релевантные автоматические проверки плюс ручные сценарии из runbook |
| Harness, команды запуска, зависимости или CI | `npm run check:full`; запуск/остановка dev и воспроизводимость установки, если затронуты |

Используйте меньший релевантный набор при разработке, полный — при изменениях на границах компонентов. После успешной проверки повторяйте её при новых изменениях или конкретном сомнении.

## Готовность изменения

Результат включает:

- изменение, соответствующее критериям приёмки;
- осмысленную регрессионную проверку для исправленной ошибки;
- результаты выполненных проверок и пути к отчётам;
- обновлённую документацию, если изменились команды или контракт;
- перечисленные ограничения и незавершённые критерии.

Правило в AGENTS.md описывает процесс. Реальные ограничения доступа задаются средой агента; обязательные проверки перед merge следует настраивать в GitHub. Этот harness поставляет CI, но не изменяет настройки защиты ветки автоматически.

Агент может выполнять локальную реализацию и проверки в пределах принятой задачи. Авторизация на внешние действия учитывается отдельно. В этой первой версии агент приносит готовое изменение для ревью; постановка задач, merge и deployment остаются управляемыми пользователем.

## Pull request и squash

В GitHub запрос на вливание называется Pull Request (PR); это аналог Merge Request (MR) в GitLab. Все изменения задачи, включая документацию, попадают в `main` через PR с методом **Squash and merge**. Прямую отправку изменений задачи в `main` не используем.

- Рабочая ветка и PR обычно соответствуют одной задаче и одному законченному результату. Внутри ветки допустимо несколько коммитов реализации и исправлений после ревью.
- После согласованной публикации рабочей ветки откройте PR с целевой веткой `main`. Заголовок имеет формат `[SS-001]: краткое описание`; в описании укажите результат, выполненные проверки и существенные ограничения.
- До merge проверьте diff, устраните замечания ревью, дождитесь успешных проверок CI и необходимой ручной приёмки. Они должны относиться к актуальной версии PR. Если появились новые коммиты, повторите затронутые проверки и ревью.
- При согласованном merge явно выберите Squash and merge. Заголовок итогового коммита соответствует заголовку PR и правилам ниже. Не переносите автоматически весь список промежуточных коммитов в тело сообщения.
- Новый коммит в `main` получает очередной тег; после проверки публикации рабочая ветка удаляется. Следующая задача начинается в новой ветке от актуальной `main`.

Итог: одна задача → один PR → один коммит в `main` → один версионный тег. Подробности метода: [GitHub Docs](https://docs.github.com/en/pull-requests/reference/pull-request-merges).

Чтобы закрепить процесс на стороне GitHub, настройте для репозитория только squash merging, сообщение squash по умолчанию из заголовка PR и защиту `main` с обязательным PR и проверками CI. Эти настройки выполняются отдельно; изменение этого документа само по себе их не включает. См. [настройку squash](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-squashing-for-pull-requests).

## Сообщения коммитов

Каждое сообщение коммита начинается с идентификатора задачи в квадратных скобках, двоеточия и пробела: `[SS-001]: commit message`. Используйте фактический идентификатор из backlog или карточки задачи; для задач harness сохраняйте их префикс, например `[HARNESS-002]: ...`.

- После идентификатора кратко и конкретно опишите изменение. Обычно достаточно одной строки.
- Добавляйте тело сообщения отдельным абзацем только при необходимости объяснить важную причину или ограничение, которые не помещаются в заголовок.
- При squash сохраняйте тот же формат итогового сообщения.

Пример: `[SS-006]: Приглушать видео во время речи участников`.

## Завершение вливания в main

Каждый согласованный PR, слитый в `main` через squash, завершается новым версионным тегом и удалением завершённой рабочей ветки. Правило относится также к изменениям только документации. Один тег обозначает итог одного PR, независимо от числа коммитов в рабочей ветке.

Разрешение пользователя на merge PR включает публикацию соответствующего тега и удаление рабочей ветки этой задачи. Повторное разрешение на эти шаги не требуется. Обычная просьба изменить файлы сама по себе не разрешает публиковать изменения: до согласованного вливания работа остаётся в рабочей ветке.

### Нумерация тегов

- Формат: `vMAJOR.MINOR.PATCH`, первый тег — `v0.1.0`.
- По умолчанию каждое следующее вливание увеличивает PATCH на один: `v0.1.1`, `v0.1.2` и далее. Изменение MINOR или MAJOR согласуется отдельно.
- Перед выбором номера обновите сведения об удалённой `main` и тегах через `git fetch origin --prune --tags`. Учитывайте опубликованные теги и локальные теги, подготовленные к отправке.
- Создавайте аннотированный тег на конкретном коммите результата вливания. В аннотации кратко укажите изменения и номера задач.
- Опубликованные теги неизменяемы. При повторной попытке отправки используйте уже подготовленный тег для того же вливания; новый номер не нужен. Если выбранное имя уже относится к другому коммиту, остановитесь и устраните конфликт без перезаписи тега.

### Порядок действий

1. Подготовьте PR по правилам выше. Завершите подходящие проверки, ревью и необходимую ручную приёмку. Проверьте чистоту рабочей копии; запомните имя рабочей ветки и SHA проверенной вершины PR.
2. Выполните согласованный Squash and merge через GitHub. Перед слиянием убедитесь, что вершина PR совпадает с проверенным SHA; при использовании API/CLI передавайте ожидаемый SHA, чтобы не слить непроверенные новые коммиты. Проверьте итоговое сообщение коммита.
3. Получите SHA результата из слитого PR и обновите локальные сведения через `git fetch origin --prune --tags`. Убедитесь, что этот коммит входит в `origin/main`. Выберите следующий свободный номер и создайте аннотированный тег именно на этом squash-коммите, а не на прежней вершине рабочей ветки или коммите следующего PR.
4. Отправьте только конкретный тег. `main` уже опубликована при merge PR; повторно отправлять её не требуется. Не отправляйте все локальные теги через `--tags`. Merge и публикация тега — отдельные операции: если тег отправить не удалось, завершите этот шаг перед следующим релизом.
5. Проверьте на удалённом репозитории целевой коммит тега и наличие результата PR в истории актуальной `main`. Для аннотированного тега сравнивайте разыменованный `refs/tags/<тег>^{}` с SHA результата PR. Если `main` уже продвинулась, тег по-прежнему относится к своему PR. При отказе отправки или несовпадении ссылок сначала устраните причину, сохранив рабочую ветку. Force-push и принудительная перезапись тегов не применяются.
6. После подтверждённой публикации убедитесь, что локальная и удалённая рабочие ветки не получили новых коммитов после проверенной вершины слитого PR. Переключитесь на `main`, синхронизируйте её с `origin/main` через `git pull --ff-only origin main` и удалите завершённую локальную рабочую ветку через `git branch -d`. Удалите также её удалённую ветку, если GitHub ещё не удалил её автоматически. Не удаляйте `main`, активные ветки других задач или ветки с незавершённой работой. Если `-d` отказывает после squash, `-D` допустим только после проверки слитого PR: его исходный SHA совпадает с текущей вершиной рабочей ветки, новых коммитов нет, а все её правки входят в опубликованный результат вливания. Без такого подтверждения оставьте ветку и сообщите причину.
7. В результате работы укажите ссылки на PR и итоговый коммит, опубликованный тег, выполненные проверки и результат удаления ветки. Сообщайте о незавершённом шаге явно.

Пример публикации тега после проверенного squash merge PR; переменные должны содержать фактические номер тега, SHA результата и имя завершённой ветки:

```sh
git tag -a "$SOFASTREAM_RELEASE_TAG" "$SOFASTREAM_RELEASE_COMMIT" -m "$SOFASTREAM_RELEASE_SUMMARY"
git push origin "refs/tags/$SOFASTREAM_RELEASE_TAG"
git ls-remote origin refs/heads/main "refs/tags/$SOFASTREAM_RELEASE_TAG" "refs/tags/$SOFASTREAM_RELEASE_TAG^{}"
```

После успешной проверки удалённых ссылок:

```sh
git switch main
git pull --ff-only origin main
git branch -d "$SOFASTREAM_TASK_BRANCH"
# Только если завершённая ветка существует на origin:
git push origin --delete "$SOFASTREAM_TASK_BRANCH"
```

## Следующий этап автономности

Текущие команды дают ненулевой код ошибки и машинную сводку с `schemaVersion`. Backlog хранит идентификаторы, статус, зависимости и критерии. Это точки подключения будущей очереди задач.

Переход к автономному режиму потребует изолированных рабочих копий, выделенных ресурсов/портов, лимита повторных попыток, независимого ревью и проверки результата перед подготовкой PR. В первой версии такого диспетчера и фоновых запусков нет.
