# Работа с harness

Работайте из Git-корня `SofaStream`, где находятся `SofaStream.sln`, `package.json` и `AGENTS.md`. Эту же папку открывайте в IDE и coding agent.

## Первый запуск

Нужны .NET SDK 10.0.102 из `global.json`, Node.js 22 или новее, Docker с Compose v2. SDK выбран точно, чтобы локальная сборка, CI и Docker использовали одну версию с файлами блокировки. При обновлении меняйте также SDK в Dockerfile. Запустите Docker Desktop перед полными проверками.

```sh
npm ci
npm run browser:install
npm run doctor
npm run check
npm run check:full
```

На Linux для первой установки браузера и системных библиотек используйте `npx playwright install --with-deps chromium` (в CI это отдельный шаг).
NuGet-зависимости восстанавливаются самим harness. Проверки используют locked mode; отсутствие или рассогласование файла блокировки завершает проверку ошибкой.

## Команды

| Команда | Результат |
| --- | --- |
| `npm run doctor` | Проверяет SDK, Node, Docker/Compose, зависимости браузерных тестов и установленный Chromium |
| `npm run dev` | Собирает API, поднимает локальную базу и фронтенд, ждёт готовности, показывает адреса |
| `npm run check` | Сборка всего решения, быстрые .NET-тесты, синтаксис JS, тесты клиента и harness; Docker не нужен |
| `npm run check:full` | Быстрые проверки, PostgreSQL/HTTP/SignalR-тесты и браузерные сценарии |
| `npm run test:integration` | Только интеграционные проверки с PostgreSQL; перед запуском собирает решение |
| `npm run test:e2e` | Только браузерные проверки; создаёт собственное окружение и собирает решение |
| `npm run diagnose` | Собирает состояние Git, инструментов, локальных контейнеров и предыдущего запуска; недоступные проверки дают ненулевой код |
| `npm run report:e2e` | Открывает последний HTML-отчёт Playwright |
| `npm run db:stop` | Останавливает оставшуюся локальную базу текущей рабочей копии, сохраняя её данные |

## Локальная разработка

```sh
npm run dev
```

Стандартные адреса: фронтенд `http://127.0.0.1:8000`, API `http://127.0.0.1:5063`, база на порту 5433. Строка подключения и CORS передаются процессу API явно. Файл `.env` и User Secrets не требуются.

Если порт занят, запуск завершится ошибкой. Можно выбрать другие порты:

```sh
SOFASTREAM_API_PORT=5163 SOFASTREAM_FRONTEND_PORT=8100 SOFASTREAM_DB_PORT=5533 npm run dev
```

Адрес API передаётся фронтенду автоматически. Имя Compose-проекта содержит хеш пути рабочей копии, поэтому разные рабочие копии используют разные контейнеры и тома. Для одновременных ручных запусков также выберите разные порты.

Ctrl+C завершает процессы API и фронтенда и выключает локальные контейнеры. Данные dev-базы сохраняются. После изменения исходников перезапустите `dev`: текущий режим запускает собранный Release API, без автоматического hot reload.

Production-файл `docker-compose.yml` остаётся отдельным. Harness использует `compose.dev.yml`, свои локальные учётные данные и только loopback-интерфейсы. Не передавайте ему строку подключения production.

## Полные проверки

Интеграционные тесты автоматически создают PostgreSQL-контейнер через Testcontainers. API запускается через WebApplicationFactory, применяет реальные миграции и использует настоящий EF/Dapper. Комнаты создаются с уникальными идентификаторами; контейнер удаляется после набора.

Браузерный набор создаёт отдельный Compose-проект, временные порты и базу. После завершения его процессы, контейнеры и тестовый том удаляются, включая обычные ошибки и прерывание процесса. Аварийное выключение компьютера или принудительный SIGKILL могут потребовать ручной очистки оставшегося проекта по его имени в отчёте.

В браузерах настоящий клиент SignalR загружается из закреплённой npm-зависимости. YouTube Iframe API заменяется управляемым тестовым плеером. Chromium использует синтетические камеру/микрофон и локальные ICE-кандидаты; реальные устройства не требуются.

Короткая нативная загрузка при Play отдельно проверяется на отсутствие цикла общей паузы/старта. Поздний вход проверяется в Playing, Paused и Buffering. Отдельные сценарии задерживают готовность API и выбранного видео (CUED); тестовый плеер отклоняет команды до CUED, чтобы выявлять преждевременное применение состояния.

Эти проверки подтверждают комнаты и передачу состояния через настоящее приложение. Они не проверяют загрузку настоящего фильма, работу RuTube iframe, слышимость видеочата или соединение через NAT/TURN.

Сценарии `youtube-loading.spec.mjs` удерживают сетевую загрузку YouTube API у гостя дольше четырёх секунд и затем освобождают её либо завершают ошибкой. Проверяются отсутствие независимого autoplay iframe, восстановление последнего видео в Paused/Playing, последующий Play/Pause и защита от позднего нативного старта. Это контролируемый API; отдельный запуск с настоящим YouTube описан в SS-010.
Стандартный сценарий входа оставляет видеочат открытым. Отдельно проверяются доступность выхода и управления видео в окнах 1280/390 px, сворачивание/восстановление, fullscreen и перетаскивание. Чат занимает собственную область страницы; в fullscreen его перемещение оставляет место для управления плеером.

## Доказательства и сбои

Каждый запуск записывает `artifacts/harness/<время>-<pid>/summary.json` и логи отдельных шагов. Сводка содержит команду, время, результат, коды завершения, имена логов и адреса собственных сервисов. `artifacts/harness/latest.json` указывает на последний результат.

Полные проверки добавляют .NET TRX-отчёты, серверные/контейнерные логи и браузерный JSON-отчёт. HTML-отчёт находится в `artifacts/playwright-report/`. В него вложены консольные сообщения обоих клиентов, а при ошибках — их снимки и отдельные traces.

```sh
npm run diagnose
npm run report:e2e
```

Сначала прочитайте провалившийся шаг и его лог. Отсутствующие Docker, SDK или браузер не превращаются в пропущенные успешные тесты. Исправьте причину и повторите соответствующий набор.
Harness не записывает содержимое `.env`, User Secrets или полный список переменных окружения; типичные пароли и токены в выводе маскируются. Перед внешней передачей отчёта проверьте его содержимое.

## Проверки внешних плееров и видеочата

Для изменений адаптера плеера или WebRTC дополнительно запустите `dev` и выполните подходящие сценарии вручную:

1. Два отдельных браузера: YouTube и RuTube по очереди; воспроизведение, пауза и перемотка ведущего видны гостю.
2. Длинное видео: управление после первого часа и получение длительности от плеера. Реализация и отдельная проверка настоящего YouTube описаны в SS-005; настоящая совместимость RuTube остаётся в SS-007.
3. Запрет камеры, только микрофон, отключение/включение медиатреков и выход из комнаты.
4. Два устройства в разных сетях: установление видеосвязи и слышимость звука.
5. Краткий обрыв сети и вход во время просмотра. SS-002 сохраняет роль/членство на 30 секунд, SS-004 восстанавливает актуальное видео и позицию; проверяйте также общую буферизацию по SS-003.
6. Громкость: выберите 60% у ведущего и 80% у гостя. Речь должна показывать Speech: 18% / 24%, после тишины возвращаются выбранные уровни. Проверьте ноль, обновление страницы и доступность ползунка в fullscreen; описание автоматических и внешней проверки — SS-011.

Записывайте плеер, браузеры, условия сети, наблюдение и ожидаемое поведение. Проверка управляемого плеера не заменяет этот результат.
